## 2. 中核となる設計判断

### 2.1 「戦術 = ショットの木」で台の図と分岐図を統一する

台の図と分岐図を別データにすると二重管理になる。そこで戦術を **ショットのツリー** として1つのデータで持ち、

- **分岐図** = ツリー全体を表示
- **台の図** = ツリー内の1本の経路（根→葉）を台の上に描画

とする。分岐図でノードをタップすると、その経路が台の図に表示される。入力も1か所で済む。

```
[根] 自分サーブ: 相手フォア前・下回転
 ├─ 相手: ツッツキ → 自分バック深く
 │    └─ 自分: バックドライブ → 相手ミドル
 │         ├─ 相手: ブロック → 自分フォア
 │         │    └─ 自分: フォアドライブ → 相手バック深く ★決め球
 │         └─ 相手: カウンター → …
 ├─ 相手: ストップ → 自分フォア前
 │    └─ 自分: フリック → 相手バック
 └─ 相手: フリック → 自分ミドル
      └─ 自分: バックカウンター → 相手フォア
```

### 2.2 ゾーンは「3列 × 3段」で深さを表現する

ユーザー要望の「2バウンド／ハーフロング／ロング」を段として持つ。

```
        相手コート（自分から見て奥）
   ┌───────┬───────┬───────┐
   │ B・L  │ M・L  │ F・L  │  L = ロング（深い）
   ├───────┼───────┼───────┤
   │ B・H  │ M・H  │ F・H  │  H = ハーフロング（出るか出ないか）
   ├───────┼───────┼───────┤
   │ B・S  │ M・S  │ F・S  │  S = ショート（台上2バウンド）
   ╞═══════╪═══════╪═══════╡  ← ネット
   │ F・S  │ M・S  │ B・S  │
   ├───────┼───────┼───────┤
   │ F・H  │ M・H  │ B・H  │
   ├───────┼───────┼───────┤
   │ F・L  │ M・L  │ B・L  │
   └───────┴───────┴───────┘
        自分コート（手前）
```

- 列（F/M/B）は **そのコートの持ち主から見た** フォア／ミドル／バック。「相手のバック深く」という会話の言い方と一致させる。
- 相手が左利きのときは相手コートの F/B の描画位置を左右反転する（データは変えない）。
- 将来 5列（フォア端・フォア・ミドル・バック・バック端）に増やせるよう、列は数値ではなく列IDで持つ。

### 2.3 ショット入力は「ゾーンをタップ → 技術をチップで選ぶ」の2ステップ

片手操作を優先し、1ショットあたりタップ2〜3回で入力できるようにする。

1. 台の図で着点ゾーンをタップ（打つ側は交互に自動決定）
2. 下から出るシートで技術チップをタップ（ドライブ／ツッツキ／フリック …）
3. 必要なら回転・メモを追加。何もしなければそのまま確定

技術チップの並びは「シェーク両ハンドドライブ型」向けにプリセットし、使用頻度順に並べ替える。

## 3. データモデル

TypeScript で記述。保存は IndexedDB（Dexie）に JSON で格納する。

```ts
// 座標系
type Side  = 'me' | 'opp';           // どちらのコートに落ちたか
type Col   = 'F' | 'M' | 'B';        // コート持ち主から見たフォア/ミドル/バック
type Depth = 'S' | 'H' | 'L';        // ショート(2バウンド)/ハーフロング/ロング
interface Zone { side: Side; col: Col; depth: Depth; }

// 技術・回転
type Player = 'me' | 'opp';
type Hand   = 'F' | 'B';             // フォア面/バック面
type ServeType = 'under' | 'top' | 'side_r' | 'side_l' | 'knuckle' | 'yg' | 'makikomi' | 'hook';
type StrokeType =
  | 'serve' | 'drive' | 'loop' | 'smash' | 'counter' | 'block'
  | 'push' | 'stop' | 'flick' | 'chiquita' | 'lob' | 'chop' | 'other';
type Spin = 'under' | 'top' | 'side' | 'none' | 'unknown';

// ショット（ツリーのノード）
interface ShotNode {
  id: string;
  player: Player;                    // 打った人
  zone: Zone;                        // 着点（side は player の相手側になる）
  stroke: StrokeType;
  hand?: Hand;
  serveType?: ServeType;             // stroke === 'serve' のとき
  serveFrom?: Col;                   // サーブを出す位置（自コートのフォア側/ミドル/バック側）
  spin?: Spin;
  isFinisher?: boolean;              // 決め球フラグ（★）
  note?: string;
  children: ShotNode[];              // 次の球の候補（分岐）
}

// 戦術
interface Tactic {
  id: string;
  title: string;                     // 例: 「フォア前下回転サーブからのバック展開」
  situation: 'my_serve' | 'opp_serve';
  goal?: string;                     // 狙い（例: 相手のバックを崩して3球目フォア）
  tags: string[];                    // 対戦相手タイプ等（例: 前陣速攻, カットマン, 左利き）
  oppHand: 'right' | 'left';         // 相手の利き手（描画反転用）
  confidence: 1 | 2 | 3;             // 自信度（練習中/実戦で使える/得意）
  root: ShotNode;                    // ショットツリーの根
  taskIds: string[];                 // Phase 2: 関連課題
  createdAt: string; updatedAt: string;
}

// Phase 2
interface Task {
  id: string; title: string; detail?: string;
  status: 'open' | 'done'; tacticIds: string[];
  createdAt: string; doneAt?: string;
}
interface PracticeLog {
  id: string; date: string;           // YYYY-MM-DD
  taskIds: string[]; tacticIds: string[];
  note: string;                       // 気づき・振り返り
}

// 設定
interface Settings {
  myHand: 'right' | 'left';
  defaultOppHand: 'right' | 'left';
  strokeOrder: StrokeType[];          // チップの並び順（使用頻度で更新）
}
```

制約:
- `ShotNode.player` は根から交互に並ぶ。`zone.side` は `player` の反対側に固定（入力時に自動設定）。
- サーブは `player === 'me'` かつ `situation === 'my_serve'` のときのみ根に置ける。
- 1経路の長さは実用上 7球程度まで。UI上の上限は設けない。

## 4. 画面構成（MVP）

```
[戦術一覧] ──タップ──▶ [戦術詳細]
    │                     ├─ 上半分: 台の図（選択中の経路を描画）
    │                     └─ 下半分: 分岐ツリー（縦型、ネスト表示）
    │                           └─ ノード「＋」──▶ [ショット入力シート]
    └─ 「＋ 新規」 ──▶ [戦術作成] ──▶ 戦術詳細へ
[設定] 利き手 / データのエクスポート・インポート / チップ並び順リセット
```

### 4.1 戦術一覧
- カード形式。タイトル、状況（サーブ／レシーブ）バッジ、タグ、自信度、ミニ台図（根から最初の決め球までの経路を縮小描画）。
- フィルタ: サーブ／レシーブ、タグ。
- 並び: 更新日順。

### 4.2 戦術詳細
- **台の図（SVG）**: 選択経路の着点を番号付き丸で描き、矢印で結ぶ。自分の球は青、相手の球は赤。決め球は星マーク。ゾーン枠は薄く表示し、S/H/L の段は横線で区切る。
- **分岐ツリー（縦型）**: スマホでは横に広がる木は読みにくいので、インデント付きの縦リストにする。各ノードは「①自分 サーブ 下回転 → 相手F・S」のような1行表示。タップで経路選択、長押しでメニュー（編集・削除・分岐追加）。
- 台の図をタップしても、その番号のノードがツリーで選択される（双方向）。

### 4.3 ショット入力シート（ボトムシート）
- 台の図（拡大）: 着点ゾーンをタップ。打つ側は自動決定なので、片側のコートのみ有効化して誤タップを防ぐ。
- 技術チップ: 1行〜2行。サーブ時はサーブ種類チップに切り替わる。
- 回転チップ、フォア面／バック面トグル、決め球トグル、メモ（任意）。
- 「保存」で確定。保存後は連続入力モード（次の球の入力へ）を選べる。

### 4.4 設定
- 自分の利き手、相手のデフォルト利き手。
- JSON エクスポート（共有シート経由で保存）／インポート。ローカル保存の唯一のバックアップ手段なので目立たせる。

## 5. 技術スタック

| 層 | 選定 | 理由 |
|---|---|---|
| ビルド | Vite + TypeScript | 軽量、PWA プラグインが揃っている |
| UI | React | Claude Code での実装効率が高く、ツリー編集の状態管理が素直 |
| 状態管理 | Zustand | 小規模なので Redux は過剰 |
| 保存 | Dexie (IndexedDB) | localStorage より容量制限がゆるく、非同期で安全 |
| 描画 | 素の SVG | 台の図はゾーン矩形＋丸＋矢印だけなのでライブラリ不要 |
| PWA | vite-plugin-pwa | オフライン動作、ホーム画面追加 |
| 配信 | GitHub Pages | 静的配信で無料。自分専用なので公開リポジトリでも問題ないが、Private + Pages も可 |
| テスト | Vitest | ツリー操作・ゾーン反転ロジックの単体テスト |

ネイティブ機能（プッシュ通知・カメラ）は使わないので PWA で十分。iPhone の Safari でも「ホーム画面に追加」でフルスクリーン起動できる。

## 8. 実装メモ（Phase 1 完了時点、2026-09-07）

設計からの変更点:
- `Tactic.root` は `ShotNode | null`。作成直後は null で、詳細画面の「1球目を入力」で根を作る。
- サーブ種類は `under / top / side_r / side_l / knuckle / yg / makikomi / backhand`。
- 軌道の矢印は進行方向の右側にわずかに膨らむ二次ベジェ。往復で線が重ならないようにするため。
- 台の色は緑（#276749）。自分＝青、相手＝赤の矢印を台の上で見分けやすくするため。
- ストアの更新は先に state を書き換えてから IndexedDB に永続化する。「保存して次の球へ」で直後に root を参照するため。
- 技術チップの使用頻度による並び替えは未実装（`Settings.strokeOrder` は固定値）。

v0.2 での変更（2026-09-07、ユーザー要望）:
- 台は青（#1d5fa8）に戻し、台の上では自分＝白、相手＝赤で描く。UI 上のバッジや番号は引き続き自分＝青、相手＝赤。
- 回転は 9 種（真上・真下・順横・逆横・順横上・順横下・逆横上・逆横下・ナックル）。`Spin` 型を置き換え、旧 `serveType` は `serveMotion`（フォア／バック／YG／巻き込み／しゃがみ込み）＋ `spin` に分離した。読み込み時に旧データを自動変換する（`store/useStore.ts` の `migrateNode`）。
- 回転の入力は 3×3 の回転ピッカー（上段＝上回転、左列＝順横、右列＝逆横、中央＝ナックル）。台の図では着点の右上にボール＋矢印のグリフを描く。矢印の向きはピッカーと同じ約束事で、物理的な回転軸を厳密に表したものではない。
- バウンドの表現: 前（2バウンド）は同じコート内に 2 つ目のバウンド点（小さな白丸）、ハーフはエンドラインまでの点線と線上のマーク、奥はエンドラインを越えて出ていく点線＋矢じり。

v0.3 での変更（2026-09-07、ユーザー要望）:
- 球の高さ `height?: 'low' | 'high'` を追加。未選択＝普通。入力は「低い／高い」の 2 チップ、台の図では着点の右下に「高」「低」の小さなバッジ、分岐ツリーでは「ツッツキ(真下・高い)」のように表示。
- 軌道の曲がりは横回転に連動させた。横回転なし＝直線、順横＝打者から見て右へ、逆横＝左へ膨らむ（右利き基準、左利きは反転。相手の球は向かい合っているので画面上は逆向き）。以前の「常に進行方向の右へ膨らむ」描画は廃止。
- 回転ピッカーは右列＝順横、左列＝逆横に入れ替え、矢印の左右が曲がる方向と一致するようにした。
- 入力シートの主ボタンを「保存して次の球へ」にし、上に配置。「保存して閉じる」は下の副ボタン。編集時は「保存」のみ。

v0.4 での変更（2026-09-07、ユーザー要望）:
- 回転グリフを「上から見たボール」に変更。順横＝時計回り、逆横＝反時計回りの円弧矢印。上下回転は中央の縦矢印、ナックルは点。左利きの打者は円弧の向きを反転する（相手の球は反転しない。上から見た回転方向は視点に依らないため）。
- バウンドの表現を矢印に変更。着点から先に細い矢印を伸ばし、前＝2つ目のバウンド点（小さな丸）で跳ね、ハーフ＝エンドライン上で止まり、奥＝点線でエンドラインを越える。サーブは自コート側の第1バウンドも小さな丸で示す。
- Phase 2 を実装。`Task`（練習課題）と `PracticeLog`（日付ごとの練習記録）を追加し、IndexedDB を v2 に。画面下にタブナビ（戦術／課題／練習／設定）。
  - 課題: 名前・狙い・やり方・関連戦術。達成チェック。課題ごとに直近の練習結果（◎○△）を表示。
  - 練習: 日付を選び、やる課題を追加、結果（◎○△）と数値メモ、その日の振り返り。過去の記録一覧から日付へ移動。
  - 戦術詳細に「練習メニュー」欄。紐づく課題の一覧、手動追加、AI コーチ呼び出し。
- AI コーチ: `domain/ai.ts`。Google Gemini API（generativelanguage.googleapis.com）を `fetch` でブラウザから直接呼ぶ。キーは Google AI Studio で発行した `AIza...` 形式。モデルは呼び出し時に `GET /v1beta/models` から取得し、`pickModel` が最新世代の Pro 系（なければ Flash）を自動選択する。設定でモデル名を手動指定することもできる。構造化出力（`responseMimeType: application/json` + `responseJsonSchema`）で 4〜6 個の練習メニューと全体コメントを受け取る。当初は Anthropic API で実装したが、ユーザーの意向で Gemini に切り替えた（2026-09-08）。システムプロンプトはトップレベルの指導者という設定で、多球・システム・ゲーム形式の組み合わせ、球出し・本数・成功の目安を具体的に書かせる。API キーは設定画面で入力し、端末内にのみ保存（エクスポート対象外）。プレースタイルの自由記述も渡す。
- エクスポート形式を version 2 に（tasks / logs を含む）。version 1 のファイルも読み込める。

v0.5 での変更（2026-09-08、ユーザー要望: 戦術の提案）:
- プレースタイル診断 `PlayerProfile`（`Settings.profile`）を追加。グリップ、ラバー、レベル、戦型、強み、弱み、得意サーブ、苦手な相手、目指すプレー、補足の自由記述。`domain/profile.ts` の `profileToText` で AI に渡す文章に変換し、練習メニュー提案でも使う。
- AI 戦術提案 `domain/aiTactics.ts`。戦術一覧の上のボタンから開く。流れは「診断の確認・編集 → 今回の要望 → （任意）コーチからの追加質問 2〜4 個に回答 → 戦術 3〜5 個を提案 → 選んで登録」。登録後は通常の戦術と同じく編集できる。タグに「AI提案」を付ける。
- AI にはショットを **フラットな一覧（id / parent / player / col / depth / stroke / spin …）** で出力させ、`buildTree` がツリーに組み立てる。再帰的な JSON スキーマを避けるため。変換時に打者を根から交互に強制し、着点の side を打者の反対側に固定、列・深さ・技術の不正値は既定値に置き換え、循環参照は打ち切る。
- Gemini 呼び出しは `domain/gemini.ts` の `geminiJson` に共通化（モデル自動選択、JSON スキーマ、エラー整形）。

v0.7（2026-09-14、ユーザー要望: ハーネス設計の見直し）:
参考: Anthropic「Harness design for long-running apps」他。原則「Agent = Model + Harness」「Guides（導く）と Sensors（測る）の2系統」「生成と評価を分ける」「エラーは主経路の一部」「関係する文脈だけ渡す」「ラチェット（退行を防ぐ）」を適用。

AI 呼び出しを `domain/harness/` に集約した:
- `runner.ts` … 実行中核。全 AI 機能（提案・追加質問・練習メニュー・審査）がここを通る。指数バックオフのリトライ（429・5xx・ネットワーク・JSON 破損）、最終トライで Flash への自動フォールバック、壊れた JSON の救済（フェンス／波括弧抽出）、トレース記録。
- `gemini.ts` … 1回だけ呼ぶ `callGeminiOnce` と `GeminiError`（status・retriable を持つ）に分離。支出上限の 429 はリトライ対象外。
- `context.ts` … 優先度付き文脈組み立て。タスク種別（提案／審査／練習）ごとに関係する知識章だけを選ぶ。全6章を毎回送っていたのを、審査は4章に削減（送信量・429 を抑制）。コーチ方針は常に最優先で末尾。
- `checks.ts` … 決定的チェック（Sensor）。打者の交互、根＝サーブ、回転と技術の整合、決め球の妥当性、相手球で終わる分岐などを LLM なしで点検。AI 提案とユーザー入力の両方に使う。
- `verify.ts` … 審査役（生成と評価を分ける）。提案とは別プロンプトの「辛口コーチ」がルーブリック（回転整合・決め球・現実性・選手適合・相手適合）で verdict（good/revise/reject）と指摘を返す。決定的チェックで error があれば AI が good でも reject に引き上げる。
- `trace.ts` … 観測（Sensor）。全呼び出しの入出力・モデル・所要時間・試行回数・エラーを IndexedDB（db v3, traces テーブル、直近40件）に記録。

UI への反映:
- 戦術提案: 提案後に別コーチが自動審査。各案に verdict バッジ（◎妥当／⚠要確認／✕非推奨）と指摘を表示。✕は既定でチェックを外す。
- 設定「AI ログ」: 直近の呼び出しを一覧・展開して、送信プロンプトと生応答を確認できる。
- 戦術詳細「セルフチェック」: 決定的チェックを自作戦術にも適用し、卓球的な気づきを表示。

eval（ラチェット）: `harness/eval.test.ts` に提案の期待判定（ok/warn/error）を固定。チェックを弱めると落ちる。単体テストは 39 件。
